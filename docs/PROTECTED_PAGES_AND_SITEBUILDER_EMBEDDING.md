# RapidForge Site Builder Embedding + Protected Pages

Thid document explains how the React drag-and-drop page builder is embedded into RapidForge and how `protected pages` are implemented.

## 1) High-level architecture

RapidForge has two relevant layers:

- Go backend (routes, handlers, templates, DB, auth)
- React page builder in `sitebuilder/` (compiled and copied into backend-served assets/templates)

Page editor runtime flow:

1. Admin opens `/pages/:id` (authenticated route).
2. Backend renders `views/page.html` (builder shell).
3. Builder shell injects `window.pageData` from Go template values.
4. React app reads `window.pageData`, allows editing, then PATCHes `/pages/:id` JSON.
5. Backend persists page metadata + rendered HTML output.
6. Public users view page via `/page/:path`.

## 2) Embedding pipeline (source of truth)

Build command:

- `make build-fe`

What it does:

1. Runs `npm run build` in `sitebuilder/`.
2. Copies `sitebuilder/dist/pages.html` to `views/page.html`.
3. Copies `sitebuilder/dist/static/*` into `static/`.

Important consequence:

- `views/page.html` is generated by the sitebuilder build. Manual edits there can be overwritten.
- Template injection logic should be changed in `sitebuilder/vite-plugin-inject-html.js` and/or `sitebuilder/pages.html` (source template).

Primary files:

- `sitebuilder/vite-plugin-inject-html.js` (injects Go-template `window.pageData` into built HTML)
- `sitebuilder/pages.html` (builder base HTML template)
- `sitebuilder/src/App.tsx` (state + save payload)
- `sitebuilder/src/PageSettings.tsx` (settings UI)
- `views/page.html` (generated output used by backend)

## 3) Protected Pages feature summary

Feature behavior:

- Admin can mark a page as protected in page settings.
- Public route `/page/:path` checks the page flag.
- If page is protected and user is not logged in, backend redirects to login.
- Redirect includes `next` so user returns to the original page after login.

## 4) Data model changes

A new boolean column exists on `pages` table:

- `protected BOOLEAN DEFAULT 0`

Migration:

- `database/migrations/20260303143000_add_page_protection.sql`

Model/persistence updates in `models/models.go`:

- `Page` now includes `Protected bool`.
- `PageData` (PATCH payload) includes `Protected bool`.
- `UpdatePageByID(...)` updates `protected = ?`.
- `SelectPageByPath(...)` selects `protected`.
- `ListPagesByBlockID(...)` selects `protected`.

## 5) Public page auth enforcement

Route wiring in `routes.go`:

- Public route remains `GET /page/:path`.
- Handler signature became `pageHandler(store, loginService)` so it can validate session token for protected pages.

Enforcement in `handlers.go` (`pageHandler`):

1. Load page by path.
2. If page is protected:
   - Read `token` cookie.
   - Validate with `loginService.LoginWithToken(...)`.
   - If missing/invalid, redirect:
     - `/login?next=<escaped original request URI>`
3. If authorized, render page HTML as before.

## 6) Login return (`next`) flow

Where `next` is set:

- In `pageHandler`, during redirect for protected pages.

Where `next` is consumed:

- `loginHandler` reads query param `next` and passes it to login template.
- `views/login.html` posts to `/login?next={{ .next }}`.
- `doLoginHandler` reads `next` and sets `HX-Redirect` to that path.

Safety constraints:

- If `next` is empty, does not start with `/`, or starts with `//`, fallback is `/blocks`.
- This prevents open redirect to external domains.

## 7) Site builder UI + payload changes

In `sitebuilder/src/PageSettings.tsx`:

- Added switch: `Protected Page (requires login)`.

In `sitebuilder/src/App.tsx`:

- `PageMetaData` now includes `protected: boolean`.
- Initial value from `window.pageData.protected ?? false`.
- Save payload includes `protected` at top-level JSON sent to PATCH `/pages/:id`.

Injected bootstrap data for builder now includes:

- `protected: {{ .page.Protected }}`

This comes from:

- `sitebuilder/vite-plugin-inject-html.js`

## 8) Related bugfix included with this feature

`sitebuilder/src/App.tsx` had:

- `active: window.pageData.active || true`

This makes `false` impossible (because `false || true` => `true`).
It was corrected to nullish behavior:

- `active: window.pageData.active ?? true`

So disabled pages now remain disabled in editor state.

## 9) Operational notes for maintainers/AI agents

When modifying builder bootstrap data:

1. Edit `sitebuilder/vite-plugin-inject-html.js`.
2. Optionally update sample object in `sitebuilder/pages.html`.
3. Run `make build-fe`.
4. Confirm generated `views/page.html` contains the new fields.

When verifying protected-page redirects:

1. Mark a page as protected in builder settings and save.
2. Open protected URL in anonymous browser session.
3. Confirm 302 location includes `next` query.
4. Log in and verify redirect returns to original `/page/...`.

If `next` seems missing:

- Ensure the running binary/templates are rebuilt and restarted.
- Check reverse proxy rules are not stripping query strings from `Location` headers.
- Inspect network `302` response directly.
